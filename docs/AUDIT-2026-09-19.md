# Denial-message audit — 2026-09-19

**Question.** For every guard that denies: does the message the person reads name a
way through that is not "turn the guard off"?

**Why it was run.** A user maintaining WordPress themes across several Local sites was
denied every cross-site edit. The message offered exactly one remedy —
`disableSecurityCategories: ["abs-path"]` — which also unprotects `~/.ssh`, `~/.aws`
and `/etc`. The scoped answer, `additionalRoots`, was never named. He uninstalled.
Fixed in v4.1.6; this audit asks how many siblings share the shape.

A guard that blocks correctly and explains badly is still a guard people turn off.
That is the whole subject here.

---

## Scope

22 hooks emit `permissionDecision: "deny"`. All 22 were classified.

## Result

**One real defect, one channel defect, twenty correct.** The product is in much better
shape on this than the field report implied — the v4.1.6 case was close to isolated.

### Fixed in this pass

| Hook | Defect |
|---|---|
| `budget-cap.sh` | The block said "use read-only tools or start a new session" and never mentioned that the cap is a value *you set*. Its sibling `tool-call-limiter.sh` has always named its knob ("raise `SESSION_MAX_TOOL_CALLS`"). A cap set too low for the job read as a wall rather than a setting. Now names `"budget"` in `.supercharger.json`. |
| `env-file-guard.sh` | **Channel, not wording.** `block()` printed "if you need this, run it in your terminal" to *stderr*, while `permissionDecisionReason` — what the model and the client actually surface — carried only the terse reason. Guidance on a channel the decider may never see is guidance that does not exist. The remedy is now in the reason. |

### Correctly absolute — a bypass would defeat the guard

`human-approval-gate`, `mcp-github-write-gate` (manual review *is* the remedy),
`workflow-pwn-guard`, `pth-persistence-guard`, `memory-write-guard`,
`artifact-publish-guard`, `mcp-playwright-guard`.

These name no way through because there should not be one. That is correct, and each
explains *why* it fired, which is the part that matters when there is no way through.

### Already good — name a real alternative, not a disable

- `mcp-sql-guard` — "open a migration PR or run via psql with explicit user confirmation"
- `tool-call-limiter` — "start a new session or raise `SESSION_MAX_TOOL_CALLS`"
- `subagent-circuit-breaker` — names the cap, and says an intentional large fan-out is fine
- `commit-guard`, `git-config-exec-guard` — both acknowledge the legitimate case and say how to proceed
- `path-guard` — as of v4.1.6
- `enforce-pkg-manager`, `tool-preferences`, `git-safety`, `harness-tamper-guard`, `readonly-guard`, `safety.sh`

## Retracted finding — do not re-raise

**`env-file-guard`'s glob/search blocks (lines ~143, ~203) are NOT the upstream
false-positive family.** This was raised during the audit and is wrong.

The guard fires only when the glob's own final component *is* a credential filename
pattern — `**/.env`, `**/*.pem`, `**/id_rsa*`. An ordinary `**/*.ts` or a bare cwd
search never trips it; both are pinned by existing tests. So it blocks a deliberate
hunt for credential files, which is correct behaviour.

The upstream complaints it was confused with — anthropics/claude-code #91681
(`Read(**/.env)` prompts on every `rg` search) and #91778 (`grep -r --include`
falsely triggers `Read(.env)`) — are about **Claude Code's own deny rules**, a
different mechanism that Supercharger does not implement. Reading the message text
without reading the trigger condition is what produced the false finding.

## Method, and the two ways it misled

Scripted classification searched each hook's string literals for remedy vocabulary.
It was wrong in both directions, and neither error is subtle:

1. **False negatives.** The first pass reported "11 of 22 name nothing at all." The
   pattern only recognised *config-shaped* remedies, so plain-English ones — "run it
   in your terminal", "open a migration PR", "start a new session" — scored as
   nothing. The real count of guards offering no path is near zero.
2. **False positives on the fix side.** The first `budget-cap` test asserted the
   message contained `budget`. The *old* message already said "Session budget cap
   reached", so it passed against the unfixed hook and proved nothing. Rewritten to
   assert `.supercharger.json`, and verified red first.

**If this is re-run:** read the trigger condition before judging a message, and check
that each new assertion fails against the unfixed hook. Both mistakes above were
caught only by doing those two things.

Script kept at `tests/`-adjacent scratch only; it is a starting filter, not an oracle.

---

## Standing check

When adding or changing a guard that denies, answer one question in the PR: *does this
message name a way through that isn't "turn the guard off" — and if not, should it?*
"No, and it shouldn't" is a fine answer. Silence is not.
