### The perf figures were measured against the wrong hook set

The README speed table and [`perf-baseline.json`](perf-baseline.json) both predated
`bab5d53`, which fixed a harness that was measuring 2 of 18 hooks. Two hooks have been
added since. So the published numbers were stale in both directions and nothing said
which. Re-measured on the same machine class; the CI row now comes from an actual run
rather than a remembered figure.

Phase 4's conclusion did not move, and is now better supported: two more hooks grew the
spawn share from 49% to 57%, so the half that optimisation could ever reach got
*smaller*.

### Both KNOWN-ISSUES narrowings fixed the shared path, not the named symptom

Each entry names one call site. In both cases every sibling had the same blind spot:

- **#6** — `hooks/bash-injection-scanner.sh` gates a structural panel on fetch
  provenance. The entry rejected these patterns after measuring 9/12 false positives on
  ordinary stdout. That measurement is correct and every false positive in it comes from
  a command that **fetched nothing** — service logs, `docker compose config`, yaml dumps,
  generated-file banners. The panel now runs only behind `curl`/`wget` at a URL,
  `gh issue|pr|release view`, `gh api`, `npm view|info`, `pip download`.
- **#5** — `hooks/safety-detect.py` resolves `$VAR` where the variable was bound to a
  credential filename, applied **once before the dispatch chain**. All eight checks read
  the same command string, so `tar czf out.tgz $F` was exactly as silent as `cat $F`.
  Fixing only the check the entry named would have left the siblings evadable by the
  identical trick.

Both entries stay **open**, narrowed. The unclosable halves are unattempted, and each
limit is asserted as a test rather than left as prose — `tests/test-var-bound-sensitive-path.sh`
contains an assertion that the split-value evasion is *not* caught, so the boundary
cannot later be mistaken for coverage.

## Rejected — do not rebuild

- **Widening the tier-1 fast-path grep to carry tier-2 seeds.** It runs on every Bash
  call and its entire value is exiting before Python. Two chained gates, the second
  fork-free, keeps the common path at one grep.
- **Variable tracking that follows every binding** (#5). The original entry is right that
  mis-tracking becomes a block on ordinary work. Only bindings whose value is *already* a
  sensitive filename are substituted — an expansion can then only insert a token that is
  blocked literally anyway.
- **Regexes for #6's last two shapes** — "exfil phrased normally" and "install
  instructions". Textually identical to legitimate READMEs. The argument is unchanged and
  preserved verbatim in the entry.
- **Optimising the hook chain at all.** Re-confirmed against the current hook set.

## Dead ends

- **Treating HOOK-LATENCY Phase 4 as unstarted.** The README figure had already landed in
  `b8a9958`; the real defect was that it was measured against a broken harness. Run
  `git log -S` on a claim before assuming an unticked box means no work was done.
- **`gh run view --job <id> --log | grep -i felt`** returns the `/perf` report, not the
  chain harness table. Use the `sed` range under *Reproduce*.
- **Benchmarking a hook copied to `/tmp`.** `lib-timing.sh` is sourced relative to
  `$BASH_SOURCE`, so it fails there, `set -e` kills the hook, and the result reads as a
  fast hook rather than a dead one. This produced a bogus 2.67 ms baseline before it was
  caught. Copy the old version into `hooks/` as a sibling instead.
