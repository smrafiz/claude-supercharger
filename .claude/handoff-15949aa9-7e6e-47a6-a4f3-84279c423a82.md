### Decisions Made
- **Measure `statusline.sh`, don't instrument it** — `lib-timing` exits at *source* time under `/sc off`, and statusline already handles the kill-switch itself at `:19`; an EXIT-trap write would also cost a real share of the 6 ms it measures.
- **Do not optimise the hook chain.** Half is process creation. Cutting the slowest hook buys ~5 ms of a 70 ms sum and nothing perceptible; fast-pathing all 17 converges on 34 ms — 17 edits to security-adjacent files for **zero** felt change.
- **Rank the event sweep by blocking cost, not sum.** By sum `PostToolUse` looks worst (391 ms) when only 33 ms blocks. Sum-ranking sends you optimising async hooks nobody waits for.
- **Report-only on perf numbers, strict on the measurement.** A slow reading is information; a perf job that measured nothing and stayed green is the failure this repo keeps finding.
- **Route new scan channels into existing hooks**, never a second scanner — one pattern list cannot drift from itself.
- **`WorktreeCreate`/`WorktreeRemove` must never be registered** (see below).

### What Failed
- **Registering on `WorktreeCreate`/`WorktreeRemove`.** My API audit ranked it the best-fitting gap. They are **provider** events — CC delegates worktree creation to a hook there and needs a path back, so a passive hook breaks `isolation: worktree` for every agent. Shipped and reverted in v2.7.26→.27; `tests/test-install.sh:242` caught me within one suite run. The docs describe the events without saying any of this. Concern moved to `CwdChanged`, which covers strictly more.
- **My 2.26.8 spawn-floor assertion** compared a 15-sample median against single-sample readings and demanded 1 ms agreement — green locally and on ubuntu, red on macOS. Fixed in 2.26.9. It also printed no numbers, because it ran under `>/dev/null 2>&1`: the same discarded-diagnostic mistake fixed in `test-install.sh` three releases earlier.
- **The first version of `test-eval-harness.sh` was decoration.** It asserted the word "FAIL" and a non-zero exit — both of which the *unfixed* harness also produces on macOS via the wrong path. All six passed against a deliberately reverted build. Now asserts the guard's own message and the exact refusal code, verified to fail against that build.
- **`display-secret-redactor.sh` shipped at 27.7 ms per assistant message** (2.26.8 → fixed 2.26.12). I forked python to parse the payload *before* the grep gate; the comment I wrote claimed the gate came first. Now 7.2 ms.
- **Two BSD/GNU traps.** `seq 0 -1` prints two values on BSD, none on GNU — so a malformed prompts file scored an agent **PASSED on Linux** and failed by accident on macOS. And `"${ARRAY[@]}"` on an *empty* array is an unbound-variable error under `set -u` on bash 3.2, killing `eval-agents.sh` before it could report anything.

### Resume With
`UserPromptSubmit` is the **largest blocking cost in the system — ~205 ms across 13 hooks, on every prompt**, nearly 3× `PreToolUse`, which is where all the tuning went. It is recorded but deliberately not acted on: the §3b concurrency finding (parallel, width ≈ 11) was measured on `PreToolUse` only, so whether these 13 parallelise is unknown and the felt figure could be a fraction of 205 ms or nearly all of it. Reconstruct the concurrency the way §3b did — enable `.profiling`, fire one prompt, rebuild each hook's `[start, end]` from the audit log, test for overlap — then decide whether 205 ms is real or bookkeeping. Do not optimise before that number exists: Phase 4 already showed this system is spawn-bound, not work-bound.
