# Changelog

## Contents

- [2.24.2] - 2026-07-29 — perf(write-wave): **three Write/Edit guards had no fast-path gate at all — chain cost down 40%.** The Bash chain had been measured and tuned; the **Write/Edit** chain never had been, and it turned out to be far worse: **20 hooks, 46.8 ms felt, 358 ms sequential**. The cause was blunt — `package-source-guard`, `install-script-guard` and `test-integrity-guard` went straight to a ~28 ms `python3` fork with **no cheap gate in front of it**, so writing a plain `.ts` file started three interpreters to discover that none of them cared. `package-source-guard` inspects seven dependency manifests; it was forking for every source file in the repo. Each now has a bash `case` gate on the raw payload, written as a deliberate **superset** of the python's own basename/path test — matched anywhere in the payload and covering the case variants python obtains via `.lower()` — so a gate miss cannot skip a file the guard would have flagged, while a spurious match simply falls through to the unchanged python. Their own suites (53 assertions) pass unchanged. Also added `python3 -S` to `code-security-scanner`, `generated-file-guard` and `file-lease` (stdlib-only, plus the local `lib_code_patterns` import which `-S` does not affect). Result: **chain sum 358 → 213 ms (−40%)**, felt 46.8 → **39.4 ms**, stable across three runs.

  **A correction to 2.24.0's research notes:** `python3 -S` was reported there as worth ~11.9 ms per fork. That figure came from timing `python3 -c pass`, where `site` really is most of the work. An interleaved A/B *inside a real hook* measures it at **~1–2 ms** — once a hook imports `json`/`re`/`hashlib` those dominate. `-S` is kept (free, no downside for stdlib-only hooks) but it is not the lever; the gates are.

  Not attempted, deliberately: gating `generated-file-guard`, now the wave's slowest hook. For an `Edit` it reads the `@generated` header from **disk**, so a payload-based gate would miss a file whose header is not in `new_string` — a wrong gate there is a missed guard, not merely a slower one. Full suite **2425/0**.

- [2.24.1] - 2026-07-29 — perf(security-path): **the same fork-free reads applied to `safety.sh` and `env-file-guard`, gated on a byte-identical fuzz differential.** These two were held out of 2.24.0 deliberately: `safety.sh` is the primary security guard and `env-file-guard` is the felt latency on `Read` (only three hooks fire there, so the slowest one *is* the wave — and `Read` is the most-used tool). Both were paying `jq` forks *before* their own fast-path exit — `safety.sh` ran one on every Bash call including the trivially-safe ones it then skips. Now they read `command`/`script`/`code`/`cmd`, `cwd`, `tool_name` and `file_path` via `lib-json-fast`, with the original `jq`→`python3` chain retained verbatim as the fallback and the exact alternation order preserved. Also removed a `mkdir -p "$(dirname …)"` (two forks per fire, for a statically-known directory). Measured: **`PreToolUse:Read` 21.0 → 12.1 ms (−42%)**, **`npm install`-class Bash 33.0 → 26.3 ms (−20%)**.

  **Verification, because this is the security path:** `fuzz-safety.sh` run before and after under identical conditions — **byte-identical across 4,655 mutations** (300 pre-existing false negatives, 0 false positives, unchanged), plus bash-evasions 14/0, PowerShell-patterns 10/0, PowerShell-parity 11/0, cmd-normalize 22/0, env-file-guard 27/0. Full suite **2425/0**.

  Two deliberate refusals: the research proposed sampling the forensic-trace trim (1-in-32) for ~2ms, which would let the log drift to ~1000±32 lines — declined, since strict behavioural equivalence on the primary guard is worth more than 2ms, and it is why `safety.sh` lands at 26.3ms rather than the projected 19ms. And `env-file-guard`'s `PROJECT_DIR` keeps its **exact** original jq expression on the fallback path, because that expression also falls back to `.workspace.current_dir` — a generic helper would have silently dropped it.

- [2.24.0] - 2026-07-29 — perf: **hot-path hooks cut to the process floor — felt latency for a typical tool call drops 47%.** Hooks were forking `jq` (~6ms) or `python3` (~30ms) just to pull one or two strings out of the stdin payload — frequently *before* their own fast-path exit, i.e. paying 30ms to decide they had nothing to do. - [2.23.48] - 2026-07-29 — feat(mcp): **your own MCP servers can now join the context-cost profiles.** Claude Code already owns *adding* a server — `claude mcp add <name> -- <cmd>`, `--transport http <name> <url>`, headers, env, `add-json` — so Supercharger deliberately does **not** reimplement that; a parallel implementation would only drift as Claude Code's config format evolves. What Claude Code has no notion of is Supercharger's **profiles**, so that is what this adds: register a server you already added and choose which profiles it belongs to. New `tools/mcp-custom.sh` — `adopt <name> [profiles]` · `list` · `remove <name>`, where `profiles` is `all` or a comma list of `light,dev,research,full` (validated up front, since a typo would otherwise silently hide the server). A registered server is configured only while one of its profiles is active, and `/sc off` moves it aside with the rest. **Prerequisite fix:** `merge_mcp_into_settings` wipes every tagged entry and rebuilds from the curated list on each switch, so a naively-tagged custom server would have been *silently deleted* on the next `/profile` — the rebuild now re-adds eligible registered servers, with the registry (`~/.claude/supercharger/mcp-custom.json`) as the source of truth, so a server excluded by the current profile is dropped from the config but never lost. The **raw entry is stored verbatim**, so http/sse/`url`/`headers` servers survive the round-trip — the curated `name|command|args|env` pipe format cannot express those. `adopt` **takes ownership** (removes the original untagged entry) rather than leaving a duplicate that would load the server twice and double its context cost; `remove` hands it back untagged so unregistering never loses a server you configured. Servers you don't adopt are never touched. +9 tests. Full suite 2398→**2407**/0.

- [2.23.45] - 2026-07-29 — perf(statusline): **cache the rendered line for one second — 42ms → 8ms per render (5.2×).** The statusline was the last unmeasured surface in the system: 562 lines, registered under `statusLine` in settings.json rather than `hooks.json`, so every hook audit and `/perf` sweep had skipped it — while it ran on *every* render. Measured at **~45ms**, and it turned out to be the largest single recurring cost in Supercharger, larger than the entire (parallel) PreToolUse chain. Two findings from the measurement: it does **not** degrade with session length (flat across a 152 MB / 76k-line transcript — it already tails the file and caches git ~3s), and the residual cost is almost entirely **interpreter startup** (bash + one `python3`), not work. Claude Code re-runs the statusLine on a **300ms debounce** — ~3–4×/second during bursts, ~150–200 executions in a 5-minute conversation — so that startup was being paid repeatedly to redraw a line that barely changes. It now serves a cached line within the same wall-clock second: repeat renders skip the python fork entirely. The cache-hit path is **pure bash parameter expansion — no fork**, or the cache would cost what it saves. Keyed on session id **+ cwd** (a `/cd` busts it), written temp-then-`mv` so a concurrent render never reads a half-written line, and skipped entirely for a session id with unsafe characters (no path escape). Worst-case staleness is <1s on a display whose git data is already 3s-stale by design; output is **byte-identical** to before, and `/sc off` still renders nothing. Fail-open throughout. +6 tests. Full suite 2385→**2391**/0.

  Also **new: `tests/perf-chain.sh`** — a hook-**chain** latency harness (HOOK-LATENCY-PLAN Phase 1). - [2.23.41] - 2026-07-28 — feat(security): **new `workflow-pwn-guard` — block the GitHub Actions "pwn request" supply-chain vector.** A `pull_request_target` / `workflow_run` workflow runs with the base repo's `GITHUB_TOKEN` + secrets; if it then checks out the **untrusted fork-PR head** (`github.event.pull_request.head.sha`, `refs/pull/N/merge`, …) and runs it (`npm ci`/build/test), attacker PR code executes with those secrets — the vector behind the **July-2026 AsyncAPI npm compromise** (GitHub shipped an `actions/checkout` v7 default-block for it in 2026).
